## What was done this session

1. **Merged scraped IBKR symbols into `CANDIDATE_UNIVERSE`** (`strategy/kairos_pipeline.py`) — `_load_scraped_ibkr_equity_symbols()` reads `data/ibkr_shortable/ibkr_*.csv` (gitignored, from last session) and merges the `yf_symbol` column into the `equity` list at import time (not pasted in as a literal — ~39k tickers would dwarf the hand-curated list). `equity` went from 57 to 38,349 unique symbols.
2. **Ran `--stage universe`, found and fixed two real bugs before trusting the result:**
   - **Currency bug**: the $50M liquidity threshold assumed USD; non-USD symbols (13 currencies across the scrape) computed a meaningless `dollar_volume`. Fixed with `usd_conversion_factor()`/`symbol_currency_info()`/`fx_rate_to_usd()` — suffix→currency map, FX rate fetched via `price_cache` (cached per run), and a specific fix for LSE's pence-vs-pounds quoting (`.L` symbols divided by 100 before conversion).
   - **`min_bars`/window-sizing bug**: Baz caught that the universe stage's history-depth threshold should be 300 (the model's real `KairosSettings.lookback`), not the old hardcoded 200 — fixed, but that surfaced a second bug: the fetch window (`400` calendar days, hardcoded) only yields ~276 real trading bars for non-24/7 markets, undershooting the new 300 threshold and failing every equity/FX symbol (confirmed live: a killed interim run showed 53/14,271 passed, *all* crypto). Fixed by reusing `calendar_days_for_bars()` (already existed in `kairos_strategies.py`, built for this exact weekday/limited-hours problem, same lineage as the BUG-10 fix) computed per-symbol instead of a flat constant.
   - Added periodic commits (every 200 symbols) + resume-on-restart (skip already-screened symbols) for crash safety on the ~4h run, with a resume-validity guard requiring the resumed `run_id` be newer than the universe run it depends on (a first version of this wrongly "resumed" an old, unrelated small-universe correlation run — fixed before real damage).
   - **Final result: 1,851 / 38,445 passed** (crypto 52, equity 1,779, FX/commodity 20). `run_id=759`.
3. **Ran `--stage correlation`, found and fixed the same class of window bug** (a hardcoded `"BTC-USD"` proxy symbol was used for *every* symbol's day-window calc, undersizing non-crypto fetches identically to the universe bug) — fixed the same way, plus added periodic commits + resumability (same stale-run-guard pattern). **Result: 1,697,403 pairs, 13,472 suggested groups.** `run_id=760`. Multi-symbol groups turned out to be **massively overlapping** — a popular symbol like TSLA appeared in 46 different candidate groups — an artifact of `greedy_group_pairs`'s per-seed clustering at this scale, not a bug in this session's changes.
4. **Built `select_deduped_groups()`** (now in `kairos_pipeline.py`) — greedy set-cover reducing the 13,472 raw groups to **961** groups that still cover every one of the 1,851 survivor symbols at least once. This is now the standard way to consume `suggested_groups` for any bulk per-group stage at this universe scale.
5. **Ran `--stage oracle` across the 961 deduped groups** via a scratchpad runner script (`/tmp/.../scratchpad/run_oracle_dedup.py` — **not** committed, still the live process's own script; do not move/delete while it's running). Benchmarked at ~62s/group. Hit and fixed a real bug in the *scratchpad script itself* (not the committed code): singleton groups were passed through as bare strings instead of 1-element lists, so `sorted()`/subprocess argv construction silently split symbols into individual characters (`"2020.HK"` → 7 separate one-char CLI args) — every singleton oracle run was failing. Fixed by having the script use the (correct) `kp.select_deduped_groups()` instead of a duplicated inline copy. Also hit a Python stdout-buffering issue (no `-u` flag → zero visible output for a couple minutes despite real progress) — fixed with `-u`.

Per Baz's direction, built `scripts/run_base_priority.py` (committed) instead of a blind full sweep: reads current `oracle_results`, ranks unprocessed deduped groups by best oracle Sharpe (unranked sorts last, re-read fresh each invocation), takes a `max_hours` budget, stops cleanly between groups (never mid-run). Launched once with an 8h budget; **Baz caught that oracle had barely started (13/961) so the Sharpe ordering wasn't meaningful yet** — stopped it. `finetuned` needs an explicit `model_path` with no obvious single checkpoint across 961 groups — held off entirely, not built out.
