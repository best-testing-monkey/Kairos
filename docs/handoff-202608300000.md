## What was done this session

1. **Exit-rule fix** (`90d9245`). `_compute_shadow_performance(naive: bool)` replaces
   two near-duplicate methods with one, sharing module-level `_resolve_exit()`
   (open-gap before intrabar, stop before target, unresolved-means-hold,
   never-resolves-means-excluded — mirrors `BacktestEngine._check_exit` minus its
   force-close fallback). `_compute_shadow_performance_naive()` survives as a
   one-line alias calling the shared method **unbound** (tests drive both against a
   bare `SimpleNamespace`). Entry anchoring is the one intentional remaining
   difference: oracle/base fill at next-bar open (bar counts, no gap check since
   there's nothing to gap against); naive fills at next-bar close (bar is spent,
   full gap+intrabar from the bar after). +5 new tests in
   `tests/unit/test_shadow_performance_multibar.py`, full suite 1790 passed.

2. **Measured the change** (`c826e10`). `scripts/ab_exit_rule.py` (kept, reusable)
   runs both rules against one oracle run's identical shadow signals — exact
   comparison, not two differenced runs. On `AAPL,MSFT,NVDA,AMD`: 1/3658 signals
   newly unresolved, median Sharpe unchanged, 33/39 strategies byte-identical. The 6
   that moved are strategies whose stop/target don't derive from the peeked bar's
   own geometry (`support_confluence` flips sign). **Base was NOT measured** (needs
   GPU) and is explicitly flagged as the stage where this should matter most, since
   model-predicted brackets miss bar-1 far more often than oracle's do.

3. **The concurrent-sweep incident.** Sibling session's `--assets-file` re-sweep of
   14 `'mixed'`-class groups (run_ids 4206–4233, oracle+naive) executed while the
   fix sat uncommitted (~20:40–21:02). Traced via three separate `ab_exit_rule.py`
   invocations against stored DB rows:
   - `GLD,HMY,SI=F,UGL` (run 4219, started 20:52:03) → **new rule**, 39/39 exact.
   - `BTG,EQX,GC=F,PPLT` (run 4206, started 20:45:39) → **old rule**, 39/39 exact.
   - So the edit landed mid-sweep: 4206–4213 (8 groups, started together) = old;
     4219 = new; 4214–4218 (5 groups, started 20:50:59–20:51:58) = unresolved,
     boundary falls in that window. Deliberately did not chase the exact boundary —
     cost ≈ cost of just re-sweeping/deleting uniformly.
   - Naive runs (4220–4233) are unaffected regardless — that path's behaviour is
     unchanged by the refactor, only its code sharing.
   - Blast radius confirmed exactly these 28 runs (both sessions ran the same query
     independently, same result) — nothing else touched the DB in that window.

4. **Recorded, then resolved, the data problem.**
   - `397d6fa`: wrote the hazard into CLAUDE.md (table of which run_ids are which
     rule, the `version`-can't-see-uncommitted-tree lesson, the re-check recipe)
