### 2. Found and fixed 3 Kairos-side bugs (all in `strategy/`)

1. **Day-1 admission gate skip** (`strategy/kairos_papertrade.py`, `main()`'s day
   loop) — `last_snapshot` is `None` on the very first iteration that places orders,
   and the admission check was skipped entirely rather than gated, letting a
   multi-position selection rule (e.g. `TOP 8`) blow past `margin_utilization_cap` in
   one ungated batch (observed 174.6% utilization on day 1 against an 80% cap).
   Fixed by building a zero-margin-used bootstrap `DailySnapshot` instead of passing
   `None`. Commit `696de76`.
2. **`compute_daily_snapshot()` understated equity** (`strategy/kairos_mtm.py`) — for
   a full-notional (spot/unleveraged, `initial_margin_pct >= 100`) position, the
   equity formula added only the P&L delta (`unrealized_pnl`), not the position's
   full current market value — but the position's full notional had already left
   `cash` at entry. This understated equity by roughly each open spot position's
   size, inflating `margin_utilization` (up to 178% observed) and risking false
   liquidation triggers. Fixed by adding the position's full current value for
   full-notional positions, keeping the P&L-delta-only path for margin-only
   positions. Commit `349500e`.
3. **Long stock/ETF positions never actually got margined in phantom**
   (`map_instrument_type()` in `strategy/kairos_papertrade.py`) — only routed a
   ticker to phantom's `instrument_type="cfd"` (the margined path) for short
   positions or FX/futures/crypto suffix patterns. A long position in a plain stock
   or ETF always got `instrument_type="stock"`, and phantom always charges full cash
   for that, completely ignoring `--max-leverage` — even though
   `ticker_max_leverage`/`classify_symbol` (Kairos's own margin config) told
   `allocation.py`'s sizing the ticker could be leveraged 5x. **This was the biggest
   of the three** — it silently capped leverage benefit to near-zero for any rule
   with meaningful long-equity exposure (found because `isolate_support_confluence`'s
   leveraged and unleveraged results were byte-for-byte identical — the user caught
   this from the results table). Fixed by reusing `_use_full_notional()`'s exact
   margin-only-vs-full-notional decision inside `map_instrument_type()`. Commit
   `84ef20d` — **not yet pushed** (see "Git state" below).

### 3. Removed now-redundant client-side compensation

- `compute_corrected_realized_pnl()` — deleted entirely. Was correcting for
  phantom's `realized_pnl` omitting `fx_conversion_cost` (pre-E17-S05); applying it
  on top of E17-S05's now-fixed `realized_pnl` would have silently double-subtracted
  the fx cost. `_close_cash_delta`/`compute_pct_profit_per_trade`/
  `build_closed_trade_equity_curve` all read `realized_pnl` as-is now.
- `_sync_margin_classes()` (still needed — see below — but simplified) now calls
  `client.brokers.update()` (E17-S07) instead of a raw SQL `UPDATE broker_profiles`.

### 4. What's still deliberately kept (not bugs, don't "fix" these)

- **`_sync_margin_classes()` itself** — still needed. Even though E17-S08 made
  phantom's bundled profiles match yfinance ticker conventions, they still use
  phantom's own *generic* IBKR rates, not Kairos's risk-tuned ones
  (`config/margin_ibkr.yaml`, e.g. `crypto_cfd` disabled entirely). This function
  overrides phantom's rates with Kairos's own.
- **`kairos_mtm.py` staying independent from phantom's `MarginEngine`** — two
  separate, still-open phantom bugs justify this (not filed as tickets, lower
  priority, flagged during earlier investigation): phantom's `Position.
  unrealized_pnl` is a permanent stub, and there's no ESMA-closeout-rule concept in
  phantom's engine. Kairos's own `liquidation_check()`/ESMA policy is deliberate,
  not a workaround.
- **`_liquidate_position()`'s SQL bypass of `ph.positions.close()`** — E17-S06 fixed
  that endpoint's cash formula, so the bypass is no longer *required*, but switching
  would also upgrade fidelity (real exit costs vs. the current zero-cost assumption)
  and changes how `corrected_cash` accounts for liquidations. Flagged as a genuine
  follow-up, deliberately not done opportunistically.
- **Kairos's admission gate only checks margin utilization %, not raw cash
  sufficiency** — found via `isolate_close_direction` showing 84 phantom fill
  rejections (since resolved by the stock-leverage fix, which was the dominant cause,
  but the underlying gap — admission_check doesn't model cash depletion within a
  batch — is still real and unaddressed). Worth a look if `phantom_fill_rejected_count`
  is ever non-trivial again after this session's fixes.
