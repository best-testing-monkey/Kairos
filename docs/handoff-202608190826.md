### 2. Bug found + fixed: equity-basis mismatch (commit `e483dc3`)

First live verification run of Stage 2.5 hit **245% margin utilization** against an
80% cap, with 3 liquidations and a wildly negative MTM return despite positive
phantom P&L. Root cause: `kairos_papertrade.py` sized new orders' EUR notional using
phantom's *raw* `account.cash`, while Stage 2.5's target was computed against
`admission_snapshot.equity` (Kairos's own MTM-corrected equity). These two diverge —
sometimes by more than the whole starting capital once shorts/financing are
involved. Fixed by sizing off `admission_snapshot.equity` everywhere in the day loop.

### 3. Bug found + fixed: cash-sufficiency gate (commit `8f50f3a`)

Re-verifying after the equity-basis fix showed **452 of 756 attempted orders**
rejected by phantom at fill time for insufficient funds — Stage 2.5's target can
legitimately ask for more real cash than exists once earlier full-notional (stock)
positions have locked equity up as share holdings rather than liquid cash.
`admission_check` only ever modeled margin utilization, never cash sufficiency.
Fixed by extending `_place_batch_orders`' existing `running_margin_used` tracker
(already threaded through a batch to catch same-batch margin cap breaches) with an
equivalent live-cash bound, checked order-by-order in placement order. A first,
cruder attempt (single aggregate pre-scale of the whole day's batch) was tried,
found to only mask the symptom via interaction with the allocation dust filter, and
reverted in favor of this precise per-order fix. Cut wasted
`PHANTOM_FILL_REJECTED` round-trips from 452 to 93 in the same live run.

### 4. Process failure discovered: account-name collision self-inflicted a false verification

Reused the same `--account-name` across 4 consecutive debug re-runs while chasing
bugs #2/#3 above, violating this project's own documented rule (`phantom_ledger`'s
`accounts.create()` doesn't enforce unique names; `positions.list(account_name=...)`
resolves via `AccountRepo.get_by_name()`, which has **no `ORDER BY`** — SQLite
returns whichever row it finds first, typically the *oldest* matching account). This
meant `main()`'s own day-loop logic (`open_tickers`/`enabled_mask`, computed via
name-based lookup) may have been reading **stale positions from the very first,
still-buggy run** for all three "fixed" re-verification attempts — which is also why
those three attempts produced suspiciously bit-identical P&L/Sharpe/trade-count
numbers despite materially different code each time. Caught by noticing the
suspicious identical-to-15-decimal-places outputs, not by the tooling. Re-ran once
more with a genuinely unique account name (`kairos_v3lev_isolate_path_hl_exec`) to
get trustworthy numbers — see below. **This gotcha was already written down in
`docs/handoff-202608181615.md`'s "Account naming matters" section; it bit anyway
because debug/iteration runs felt like they didn't need a fresh name each time. They
do, always, no exceptions — even for a "just rerun it real quick" check.**

### 5. True verification result (clean account) + user decision on residual drift

With a clean account, `isolate_path_hl_exec` (no-crypto, leveraged) showed margin
utilization still peaking at **226%** during a drawdown, with 7 liquidation
events (only 2 positions actually force-closed, both near-flat P&L). Root cause:
Stage 2.5 only sizes *new* orders each day; it never trims already-open positions.
When a losing streak shrinks equity, already-open positions' fixed-€ margin
footprint becomes a larger fraction of the smaller equity base, without any new
order ever being placed. This was presented to the user as a real design choice
(add active rebalancing of existing positions vs. accept liquidation as the sole
backstop). **User's explicit decision: accept liquidation as the backstop, no
active rebalancing.** Rationale given: every position already carries its own
stop-loss. Verified as a follow-up that stop-loss genuinely IS checked before
margin-call each day (`runner.backtest()` — phantom's SL/TP engine — runs before
`liquidation_check()` in the day loop), and that the 2 actual liquidations were
portfolio-level margin-call events (aggregate margin usage over threshold),
independent of and prior to either position's own stop being touched — matches real
broker margin-call behavior. **No code change from this finding; it's accepted
as-is.**
