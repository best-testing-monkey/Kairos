## What was done this session (since the 16:29 handoff)

**Methodology discussion (unresolved, worth revisiting):** Baz noticed the batch's finetuned-vs-base mean_sharpe jumps are far bigger than typical 1d improvements (1d: ~1-2 points; 1h: often 10-30 points). Investigated and explained two real, non-bug contributors: (1) `bars_per_year("1h") = 6048` vs `bars_per_year("1d") = 252` means 1h's Sharpe annualization multiplier (`sqrt(6048)≈77.8`) is ~4.9x bigger than 1d's (`sqrt(252)≈15.9`) — a mathematically expected scaling, not evidence of anything. (2) `mean_sharpe` is computed only over "viable" strategies (`sharpe>0 AND signal_count>=3`), i.e. already cherry-picked winners — a selection-bias inflation baked into the reporting metric itself, present at both intervals but proportionally louder once the base scale is ~5x bigger. Spot-checked two accepted models' underlying signal counts: UNI7083-USD's top performers have deep sample sizes (hundreds to thousands of signals, not a fluke); CRM's *top* strategy has only 4 signals (right at the edge of statistically meaningless). **Net: mixed evidence, not conclusively good or bad — this needs the actual persistence check (below) before trusting the batch's accept/reject verdicts as real, durable edge.**

**Investigated whether finetune verification predictions are cached** (Baz's precise question): confirmed **no** — `run_stage_finetune_next`'s calls to `run_stage_model` pass no `extra_env`, so `KAIROS_PRED_CACHE_DIR` is never set during verification, and that cache is strictly opt-in. Separately confirmed `kairos_signal_replay.py --precompute` reads only from `signals_cache` (populated by `kairos_signals.run()`, a different code path finetune_next never calls) — so even if predictions were cached, replay wouldn't see anything for these new checkpoints yet regardless.
