Investigation confirmed: the 3 `failed` 1h finetune registry rows (COST, JTO-USD, HBAR-USD, all dated 2026-08-04) have training windows crossing DST fall-back boundaries — strong circumstantial evidence they died to BUG-03/BUG-04 (fixed 2026-08-20, before this session even started). - **Found and fixed a second real bug**: `select_finetune_candidate` never accepted/respected an interval filter, and `run_stage_finetune_next` never forwarded its own `interval` argument into it — auto-select ranked globally across 1d+1h combined, and since 1d has far more accumulated history it would always win. Every existing 1h registry row was necessarily created via manual `--assets` requeue, never natural auto-select. Fixed by adding an `interval` parameter to `select_finetune_candidate` and threading it through. (First attempt had a variable-shadowing bug — `interval_filter = interval` was placed after a loop that reassigns the local `interval` variable, silently capturing the wrong value; caught via a new regression test before landing.) Committed `a922a76`. Full suite green (1689 passed, same pre-existing unrelated failure).
- Calibrated real finetune training wall-clock time against COST (2 timed runs, 1 epoch and 20 epochs): ~305s fixed overhead (data fetch + model/tokenizer load) + ~0.17s/training-step. Also found COST's validation loss is best at epoch 1 and gets steadily worse every epoch after (severe overfitting on its small dataset — only 1504 bars of real 1h history exist for it despite requesting the full 2-year window, since equity intraday data only covers trading hours). The trainer always keeps the best-val-loss checkpoint, so this never corrupts the deployed model, but it means blindly inflating epoch count to hit a fixed wall-clock target wastes GPU time on small/single-symbol candidates for zero benefit.
- Asked Baz how to handle that tradeoff; he chose "scale epochs to data size, cap waste." Built `run_finetune_batch_1h.py` (throwaway orchestration script, kept in the session scratchpad, not the repo) implementing: `epochs = clamp(round((1500s - 305s) / (steps_per_epoch * 0.17s)), 10, 30)` — floor 10 (the existing proven default both accepted 1h models used), cap 30 (bounds overfitting waste).
- First batch launch immediately hit a real operational bug: `run_stage_finetune_next`'s GPU-idle check (threshold ~10%, GPU was briefly at 23-45% from an unrelated background process) causes it to skip and return immediately — my first script version treated a skip identically to a completed cycle and would have burned through all 18 candidates in seconds doing nothing. Caught immediately by checking the log right after launch. One candidate (JTO-USD) got lucky and actually started real training in that same window before I killed the driver process — its child training subprocess survived the kill (orphaned, not matched by the pkill pattern) and kept running for real, so it was left alone rather than wasted.
- Baz asked whether the retry-wait was long enough for a 25-minute training session and asked for a 60-minute cap (previous version retried every 90s indefinitely, no cap at all — not actually too short, but he wanted an explicit bound). Added `MAX_TOTAL_WAIT_SECONDS = 3600`: after an hour of cumulative busy-skips for one candidate, the script logs "GAVE UP" and moves to the next rather than hanging forever.
