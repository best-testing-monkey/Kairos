# BUG-03 — DST-ambiguous-time crash in the local-fallback hourly fetch path

**Goal:** `kairos/data.py`'s `fetch_price_data_local_fallback` crashes with `Cannot infer dst time from 2025-11-02 01:00:00 as there are no repeated times` whenever an `1h`-interval fetch window spans a US DST fall-back date (currently 2025-11-02) — found live during E11-S02's verification run, where it caused universe screening to fail 152/153 `1h` symbols. Fix the underlying `tz_localize` call to handle ambiguous DST times instead of raising.

**Context:**
- Found and root-caused (but not fixed) by `docs/tickets/E11-S02-correlation-live-verify-and-playbook.md`'s live run — see `docs/playbooks/hourly-correlation.md`'s "Separate finding" section for the original observation (149+ crypto symbols failed `--stage universe --interval 1h` with this exact error on 2026-08-20).
- `kairos/data.py`, function containing this exact line (search `tz_localize("America/New_York")`, ~line 179):
  ```python
  df["Date"] = pd.to_datetime(df["Date"]).dt.tz_localize("America/New_York")
  ```
  This reads OHLCV rows out of a local sqlite DB (`prices` table, naive datetime strings with no timezone info — see the `SELECT date, open, ...` query a few lines above, ~line 162) and localizes the `Date` column to US Eastern time as a single bulk operation. Pandas' `tz_localize` defaults to `ambiguous="raise"` — on the "fall back" DST transition (clocks go back an hour, so one wall-clock hour occurs twice), a NAIVE timestamp reading `01:00:00` doesn't tell pandas whether it means the first or second occurrence of that hour, and it raises rather than guessing, by default.
  - This is a genuinely ambiguous case only for **hourly-or-finer** intervals — a `1d` fetch never has two rows both timestamped inside the same repeated hour, so this bug is intraday-specific, which is exactly why it surfaced now (this is the local-fallback path for `1h` fetches specifically, and yfinance's 729-day `1h` history cap means "today" has now advanced far enough that the lookback window spans the most recent Nov DST date).
- This function is `fetch_price_data_local_fallback` — per `strategy/kairos_strategies.py`'s own docstring (search `fetch_price_data_local_fallback` usage, `fetch_data_raw`), it's a FALLBACK path used "when the primary price_cache fetch returns empty... observed in production: a finetune_next backtest crashed here for a symbol whose training fetch, moments earlier in the same run, had already succeeded via this exact fallback." So this function firing at all (not just crashing) is already a fallback-of-last-resort path — the fix should make it not crash, without needing to reason about why the primary fetch was empty in the first place (out of scope here).
- pandas' `Series.dt.tz_localize()` accepts an `ambiguous` parameter: `"infer"` (attempt to infer from the order of the data — works when timestamps are monotonically non-decreasing, which sorted OHLCV rows should be, per the `ORDER BY date` in the SQL query a few lines above) or an explicit bool/bool-array. It also accepts `nonexistent` for the (different, unrelated) DST "spring forward" gap case — include a safe `nonexistent="shift_forward"` alongside the `ambiguous` fix for completeness, since that's the same class of DST edge case on the other transition and costs nothing extra to handle.
