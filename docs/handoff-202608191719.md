## What was done this session

### 1. Crypto-inclusive 14-rule batch under margin-utilization-target sizing

Forked a background task (`fork` subagent) to launch `results/run_v3levcrypto_batch.sh`,
which re-ran all 14 selection rules (crypto-inclusive, not the no-crypto
variants already covered in prior sessions) through `kairos_papertrade.py`
with `--max-leverage 30 --margin-utilization 0.8`, one fresh
`kairos_v3levcrypto_<rule>` account per rule. **Important harness nuance
learned this session**: the fork used a detached (`nohup`) shell process to
run the ~2.5–3hr batch, which the harness doesn't track as a "live child" —
so the fork's own task showed `status: completed` almost immediately, well
before the actual batch finished. I took over monitoring directly with a
persistent `Monitor` polling `results/v3levcrypto_batch_progress.log` every
30s (with driver-process liveness/crash detection), rather than trusting the
fork's completion status. All 14 rules finished cleanly (exit 0) after ~2h45m.

Extracted final stats from each rule's output JSON and republished the
existing **"Margin Target Verification"** artifact with a new section: a
3-way comparison (old crypto-inclusive Kelly-only / no-crypto under the
target / crypto-inclusive under the target) for all 14 rules. Two gotchas
hit and fixed during extraction, worth knowing if re-deriving these numbers:
`mtm_margin_utilization_peak` in the result JSON is a **fraction**, not a
percentage (×100 needed); and the artifact's "max DD" column uses
`pct_max_drawdown`, not `mtm_max_drawdown_pct` — the two differ meaningfully
and only one matches the artifact's existing convention.

**Headline finding**: `isolate_path_hl_exec`, which looked like the
roughest no-crypto rule (7 liquidations, 226.5% peak utilization), is
actually the strongest candidate crypto-inclusive — Sharpe improves
1.74→2.32, liquidations drop to **zero**, peak utilization falls to 151.8%,
still +46.3% return. Crypto exposure was diversifying away the liquidation
risk that excluding it had concentrated, not just adding return. This
**revises the shortlist from earlier in this session** (see "Concluded
threads" below) — `isolate_path_hl_exec` and `exclude_bad_top8` are now the
top two candidates, not `exclude_bad_top8` alone. `exclude_bad_top3_ev`
stays interesting (Sharpe 1.65 crypto-inclusive, sample grows from 33→164
trades) but still worth the longer-window follow-up already flagged in
prior sessions. Three rules (`isolate_close_direction`, `inverse_variance`,
`path_v_shape`) trade zero crypto — identical no-crypto/crypto-inclusive
results by construction, consistent with prior findings, not a bug.

**Real bug found and fixed during this step**: the first `systemctl --user
status` showed the timer's next fire time as `00:05:00 CEST` (local time),
not UTC — `OnCalendar=` without an explicit `UTC` suffix runs in the
system's local timezone, so my original `OnCalendar=*-*-* 00:05:00` (no
suffix) would have drifted by an hour every DST transition even though the
wall-clock trigger stayed fixed. Baz confirmed he wants a true UTC instant,
so it's now `OnCalendar=*-*-* 00:05:00 UTC` — verified via `systemctl --user
list-timers` showing `Thu 2026-08-20 02:05:00 CEST` (= `00:05:00 UTC`,
correct). **The two pre-existing default timers
(`kairos-daily-signals.timer` at `02:00`, `kairos-weekly-discovery.timer`
at `04:00`) have the exact same latent bug** — their descriptions and
`systemd/README.md` claim "UTC" but their `OnCalendar=` lines have no `UTC`
suffix, so they actually fire at local time too. Documented in
`systemd/README.md`'s Scheduling section (with a note), **not fixed** —
out of scope unless Baz wants it touched, since those two units' actual
behavior may already be relied upon as-is.

`systemd/README.md` updated: new unit added to the Install/Verify/Logs
sections' command lists, Scheduling section documents all three timers
