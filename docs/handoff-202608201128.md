### 4. Production incident the next morning — two real bugs found and fixed

Baz reported: no Telegram from the daily job that morning, and a separate
Telegram GPU-lock-error message at `2:10`. Root-caused both:
- **Silent Telegram delivery failure** (`scripts/kairos_daily_signals.py`,
  `scripts/kairos_weekly_discovery.py`): neither script passed
  `parse_mode=None` to `send_telegram()` (default is `"Markdown"`), unlike
  every other notifier in the repo. A strategy name with an underscore
  (`path_execution`) broke Telegram's Markdown parser and silently dropped
  the whole success message. Fixed in all 8 call sites across both scripts
  (commit `26529fc`), verified live with an underscored strategy name
  (`expected_value`) delivering cleanly afterward.
- **GPU-lock scheduling collision**: the old default `kairos-daily-signals.timer`
  (`02:00` local, coincidentally ≈`00:00 UTC` in CEST) held the GPU lock for
  1h47m that morning; the new `nc-top8` job fired 5 minutes later and gave
  up after the lock's 300s wait. This pattern had already bitten
  `kairos-weekly-discovery.timer` once before (2026-08-17), independent of
  this session's changes. **Resolved by Baz's explicit call**: the old
  default timer is "outdated" — disabled and stopped
  (`systemctl --user disable --now kairos-daily-signals.timer`), not
  deleted, trivially re-enableable. `nc-top8` is now the only daily job, no
  collision risk. Also surfaced along the way: `kairos-idle-finetune.timer`
  is disabled (not a factor) and its `.service` is broken (`CHDIR` error —
  stale unit referencing the `kairos_idle_finetune.py` script deleted
  2026-07-26). Flagged, not touched.

### 6. `gross_cap_pct` bug — found, mis-fixed, then corrected

Baz noticed the report only used 8% of the 80% margin target on a real run
(2 candidates, IWM 5x + SPY 20x). Root cause: Stage 3's gross notional cap
(`gross_cap_pct`, default 100%, calibrated for the pre-leverage cash-only
world) was silently undermining Stage 2.5's margin target whenever leverage
is uneven across selected instruments — Stage 2.5 correctly sized toward
80% margin (requiring >100% notional given the leverage mix), and Stage 3
scaled it back down to fit 100% notional, dragging margin utilization down
by the same factor. **First fix attempt (commit `4ed462d`, later reverted
in spirit) was wrong**: special-cased `allocation.py`'s `size_selected()` to
skip Stage 3 entirely when `max_leverage > 1.0`. Baz caught this — the
actual, correct fix (commit `d303854`) is that `kairos_papertrade.py`
*never* skips Stage 3; it sets `gross_cap_pct = 100 * args.max_leverage`
so the cap is just generous enough not to bind. `kairos_signals.py`'s
config was missing this line entirely (defaulting to the unleveraged 100).
Fixed at the actual mismatch site, `allocation.py`'s `size_selected()`
reverted to its original leverage-agnostic form (kept as a pure function of
`(candidates, config)`, matching its own docstring's stated design intent).
Verified live: today's real margin usage went 8% → unchanged 30% after this
correction (still capped by the separate `max_pos_pct=15%` per-position cap
and thin signal quality that day — 6 of 8 TOP-8 candidates dust-filtered) —
confirming the report's config now genuinely matches what papertrade would
have produced, not that the underlying candidates changed.

Discussed raising `max_pos_pct` (currently 15%, used globally — papertrade,
this report, and `kairos_signal_replay.py` all share the default, so
raising it would invalidate the 14-rule verification numbers until
re-checked) to let thin days approach the 80% target more easily. **Decided
to leave it at 15% for now** — not changed.
