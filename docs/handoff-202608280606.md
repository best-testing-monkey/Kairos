The genuinely correct multi-bar mechanism (hold until a real stop/target trigger, across as many bars as it takes, excluding the signal if data runs out first) already exists elsewhere — `BacktestEngine._check_exit`/`_calculate_pnl`, exactly as `kairos_signal_replay.py` already uses it (loop bars, stop on `_TERMINAL_EXIT_REASONS = {"stop_open","target_open","stop","target"}`, treat "close" as "keep holding," disqualify if bars run out). 5. **Implemented `lagged_oracle` mode**, reusing that exact multi-bar contract but reimplemented as a lightweight plain-Python/pandas loop (no `BacktestEngine`/phantom_trader dependency — confirmed explicitly when Baz asked "did you use the cheap method?"):
   - `OrchestratorConfig.lagged_oracle: bool = False` (`kairos_orchestrator.py`)
   - `KairosOrchestrator._compute_shadow_performance_lagged()`: takes oracle's real shadow signals (`(date, symbol, strategy, direction, stop, target, entry)`, already recorded, unchanged) — re-anchors entry to the real bar oracle already peeked at (`future.iloc[0]`, its **close**, not open), recomputes stop/target from the same relative offsets, then walks `future.iloc[1:]` bar by bar with the same open-gap-then-intrabar contract as `_check_exit`, breaking on a genuine trigger or excluding the signal entirely if data runs out.
   - `--lagged-oracle` CLI flag (`kairos_strategies.py`, implies `--no-prediction`, mutually exclusive with `--naive-baseline` — guarded with `parser.error()`).
   - `kp.run_stage_lagged()` (`kairos_pipeline.py`): mirrors `run_stage_naive()`, writes `stage='lagged'` rows to the same `oracle_results` table, deliberately skips `refresh_disabled_strategies()` for the same reason naive does.
